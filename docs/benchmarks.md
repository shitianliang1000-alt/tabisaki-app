# 旅程の成立率（Benchmarks）

組んだ旅程が「本当に回れるか」を、決まった頼みごとで毎回同じように測ります。
知識ベース（`kb/`）や旅程を組む部分（`js/`）を変えたとき、良くなったか悪くなったかを数字で比べるためのものです。

```sh
node tools/plan_bench.mjs                    # 1本ずつの結果と、成立率
node tools/plan_bench.mjs --check            # 基準より悪ければ終了コード 1（CI と同じ）
node tools/plan_bench.mjs --only random-374-02   # 1件だけ組み直す（失敗の再現）
node tools/plan_bench.mjs --out bench-out    # 不成立の旅程を bench-out/failures/ に1件ずつ保存
node tools/plan_bench.mjs --write-baseline   # 今の結果を基準にする
node tools/plan_bench.mjs --sweep 20         # シード 1〜20 をまとめて走らせる（基準とは比べない。約7分）
```

通信はしません（AI・経路・天気は使わず、距離からの目安で組みます）。シードと日付を固定しているので、同じ `kb/` と `js/` なら何度走らせても同じ結果になります。1回およそ30秒です。

## 頼みごとの組

| 組 | 中身 | 件数 |
|---|---|---:|
| `fixed` | [bench/requests.json](../bench/requests.json)。地域・日数・出発地・移動の手段・曜日（月曜の休館を含む）を散らした、決まった頼みごと。`fixed-25` から後ろは、実際に不成立だった頼みごとを壊れかたごとに1本ずつ固定したもの | 34 |
| `random` | 地名×したいこと×出発地×日数（1〜4日）×日付×時刻×手段を、シード 374 の乱数で選んだもの（`randomRequests`） | 60 |
| `tight` | 遠くへ、短く。1〜2日・帰りは 17〜19時に絞ったランダム（`tightRequests`）。現地にいられる時間が短い旅でしか出ない壊れかた（帰りの時刻を過ぎる・着く前に予定が始まる・立ち寄りが入らない）を濃く引きます。2割ほどは「往復できません」と断るのが正しい答えです | 60 |

直したあとは `--sweep` で、基準とは別のシードでも成り立つかを確かめてください。基準のシードの不成立だけを消す直しは、別のシードで同じ壊れかたを残します。

`fixed` の id を変えたり消したりすると、基準と比べられなくなります。足すときは末尾に足して、基準を作り直してください。

## 調べること

1本の旅程に、下の「不成立」の種類が1つでもあれば不成立です。**成立率 = 不成立の無い旅程 ÷ 全部**。

| 種類 | 何を見るか | 不成立に数える |
|---|---|:---:|
| `crash` | 組めなかった（例外） | ✅ |
| `empty` | 立ち寄りが1つも無い（移動だけの旅程） | ✅ |
| `hours` | 営業時間の外・最終入場の後・休みの日に立ち寄る（実データの時刻。`packages/core/src/hours.js` の `hoursFor` で判定） | ✅ |
| `travel` | 帰りの時刻を過ぎる・出発より前に動く・地上で時速 320km を超える移動・1本で12時間を超える移動 | ✅ |
| `duplicate` | 同じ場所に2回（同じ id、または 100m 以内） | ✅ |
| `constraint` | 予定が重なる・終わりが始まりより前・日数が頼んだ数と違う | ✅ |
| `hoursEstimated` | `hours` と同じ判定を、分類ごとの目安の時刻で行ったもの。実際の時刻が分からないので数だけ出します | — |
| `unreachable` | 「この日程では往復できません」と断った（札幌から倉敷へ日帰り、など）。頼みごとの方が無理なので、正しい答えです | — |

判定の関数は `tests/plan-bench.test.js` が、手で作った旅程で確かめています。

## 基準と回帰

基準は [bench/baseline.json](../bench/baseline.json) です。CI（`test.yml` の `bench`）は PR ごとに走らせ、次のどれかで失敗にします。

- 成立率が基準より **3ポイント**を超えて下がった
- 不成立の種類のどれかで、該当する旅程が基準より **2本以上**増えた
- 基準では成り立っていた頼みごとが、新しく不成立になった

許す幅は `bench/baseline.json` の `tolerance` で変えられます。結果は実行のまとめ欄（Summary）に表で出て、不成立の旅程は `plan-bench` の添付に1件ずつ入ります（`reproduce` に再現の手順）。

良くなったときや、変更で旅程が変わるのが正しいときは、`node tools/plan_bench.mjs --write-baseline` で基準を作り直し、同じ PR に入れてください。

## 最初の基準（2026-10-27）

| 指標 | fixed | random |
|---|---:|---:|
| 旅程の数 | 24 | 60 |
| **成立率** | **100%** | **81.7%** |
| 立ち寄りが無い | 0 | 2 |
| 営業時間の外（実データ・目安） | 0 | 0 |
| 移動時間の超過 | 0 | 9 |
| 同じ場所に2回 | 0 | 0 |
| その他の制約違反 | 0 | 0 |
| 往復できないと断る | 0 | 1 |

見つかった不成立は、主に2つの形です。

- **遠い出発地からの最終日の帰り**が、帰りの時刻を数分〜1時間半過ぎる（那覇→名古屋、函館→東京など）
- **鉄道で行けない遠い場所へタクシーで移動**する（札幌→奄美を「タクシー約3,467分」）。経路 API を使わないときの目安の組みかたの穴です

どちらも旅程を組む部分の直しで、このベンチマークで直ったかを確かめられます。

## 帰りの時刻を守る直し（2026-11-10）

上の「遠い出発地からの最終日の帰り」を直しました。原因は1つではなく、**検証（`verify.js`）と組み立て（`planner.js`）が、別の時計・別の所要時間を見ていた**ことから出る壊れかたが5つありました。

| 壊れかた | 実際に出ていた旅程 | 原因 | 直し |
|---|---|---|---|
| 最終日の昼食で帰りが遅れる | 10:20 見学が終わる → 12:00 昼食 → 13:00 函館発 → 19:30 東京着（期限 18:00） | 締めの昼食を「空いている時刻」に置くだけで、時計を進めていなかった。検証は 10:20 発で間に合うと見ていた | 最終日の食事は、食べ終わってから帰って間に合うときだけ置き、時計も進める。置けなければ「移動の途中で」と旅程に書く |
| 帰りの所要時間が検証と違う | 冠着山 → 広島駅が 18:09 着（期限 18:00） | 帰りの行を「出発地 → 拠点の駅」の時間（往路の写し）で組んでいた。検証は「最後の立ち寄り → 終点」 | 検証で使った数字（`result.back`）をそのまま帰りの行に使う |
| 着く前に次の予定が始まる | 06:30–11:28 札幌駅 → 箱根湯本駅／11:07 箱根湯本温泉へ移動 | 実際の時刻で組み直して1か所も入らないとき、古い立ち寄りに新しい往路をつないでいた | 時刻と立ち寄りは同じ回のものを組で使う。組にならなければ前の回のまま |
| 立ち寄りが1つも無い | 博多 → 名古屋、112分の自由時間、帰る | 先に昼食を取って時間が尽きる／先頭の長い場所が入らないと、後ろの短い場所まで全部外す | その日まだ何も回っていなければ立ち寄りを先に。入らない場所だけを飛ばして次を試す。それでも無ければ拠点の近くから探し、そう書く |
| 1日ぶん消える | 4日の旅程が3日ぶんしか出ない（16:02 着の1日目に、2日目の場所まで全部外れる） | 閉まっていた場所を、翌日に試さずその場で外していた | 翌日に1回だけ持ち越す。開館待ちが長い場所は、順番を1つ後ろへ送ってから試す |

あわせて、飛行機の速さで見積もった区間（札幌 → 那覇など）には「飛行機を使う見込み」と書くようにしました（何に乗るとも書かずに、新幹線より速い地上の移動に見えていました）。「必ず行く」場所を削れずに帰りが期限を過ぎるときは、旅程に「約◯分過ぎます」と出ます（`lateReturn`）。

| 指標 | fixed（33本） | random（60本） | tight（60本） |
|---|---:|---:|---:|
| 成立率（直す前） | 72.7% | 81.7% | 70.0% |
| **成立率（直した後）** | **100%** | **100%** | **100%** |
| 移動時間の超過（前 → 後） | 5 → 0 | 9 → 0 | 13 → 0 |
| 立ち寄りが無い（前 → 後） | 2 → 0 | 2 → 0 | 2 → 0 |
| その他の制約違反（前 → 後） | 3 → 0 | 0 → 0 | 3 → 0 |

「直す前」は、同じ頼みごとを直す前のコードで組み、いまの判定で数えたものです。基準とは別のシード（`--sweep 25`、3,000本）でも確かめています。この3,000本で1本だけ不成立が残っていたので（名古屋から三原へ日帰り・現地102分。最初の候補が入らないまま昼食に60分を使い、歩いて行ける神社まで入らなくなっていました）、直して `fixed-34` に固定しました。表の fixed は、それを足す前の33本の数字です。旅程の中身は、ランダム240本の合計で 1日あたりの立ち寄りが 3.60 → 3.65 か所、立ち寄りの無い日が 9 → 4 日、昼食・夕食の行が 923 → 891 です（減った32は、帰りに間に合わせるために取らなかった最終日の昼食です）。

通信をしない測りかたなので、実際の時刻表での成立率ではありません。ただ、直したのは検証と組み立ての食い違いで、時刻表を引いたときも同じ道を通ります。

## 知識ベースの点検

旅程とは別に、`kb/` そのものの壊れかたは `tools/kb_check.mjs` が見ます（必須の項目・座標が日本の中か・id の重なり・知らない分類・営業時間の形・索引の件数）。PR ごとの単体試験と、週に1回の `kb-check.yml` で走ります。詳しくは [knowledge-base.md](./knowledge-base.md) です。
