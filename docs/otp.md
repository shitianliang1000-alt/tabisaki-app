# OpenTripPlanner で乗り換え検索を手元で動かす

GTFS-JP（時刻表）と OpenStreetMap（道路・歩道）を読ませた OpenTripPlanner（OTP）2.6.0 を自分の機械で動かし、
旅さきの乗り換え検索（`POST /transit`）から使う仕組みです（Issue #429）。
「徒歩→バス→鉄道→徒歩」のような乗り継ぎを、1回の問い合わせで、実際の時刻表どおりに返します。

- 構成: `compose.yaml` の `otp-build`・`otp`（公式イメージ `opentripplanner/opentripplanner:2.6.0`、版を固定）
- 設定: `otp/router-config.json`（歩く速さ 1.2m/秒＝時速4.3km など）・`otp/otp-config.json`
- 地域: `otp/regions/kumamoto.json`（はじめの地域。下の「なぜ熊本か」）
- データ集め: `tools/otp_fetch.py`
- つなぎ: `server/transit.js` の `otp`（Cloudflare 版の中継と、Node 版の中継 `server/node-proxy.mjs` の両方）
- 測定: `tools/otp_bench.mjs`

## 動かしかた

```sh
python3 tools/otp_fetch.py                        # 時刻表 6本と地図を data/otp/kumamoto/ に（1分ほど。地図の元は 350MB）
docker compose --profile otp run --rm otp-build   # 経路網を組み立てる（47秒、graph.obj 55MB）
docker compose --profile otp up -d otp            # http://127.0.0.1:8080/otp/gtfs/v1 で答える（起動 20秒ほど、メモリ 1.2GB）
```

中継に `OTP_URL` を入れると、乗り換え検索で**いちばん先に** OTP を試します。

```sh
OTP_URL=http://127.0.0.1:8080 node server/node-proxy.mjs        # Node 版の中継
npx wrangler dev --var OTP_URL:http://127.0.0.1:8080            # Cloudflare 版を手元で
```

Cloudflare に置いた中継から使うときは、OTP を HTTPS で外から届くところに置き、その URL を
`npx wrangler secret put OTP_URL` で入れます。OTP には認証が無いので、そのときは手前で
アクセスを絞ってください（Cloudflare Tunnel と Access など）。手元で使うだけなら、compose は
127.0.0.1 にだけ出しています。

OTP が答えられないとき（時刻表の範囲の外 `OUTSIDE_BOUNDS`・歩くだけの答え・終電の問い合わせ・
位置の無い問い合わせ）は「経路なし」として、いつもの順（駅すぱあと → … → Transitous）に回ります。
OTP が止まっていても、旅程づくりは止まりません。

## 1回で引けることの確認

熊本駅から熊本電鉄の御代志駅まで、平日の朝9時に聞いた答えです（`tests/fixtures/otp-kumamoto.json`。
テストは、この本物の答えを読み替えて確かめています）。

| 区間 | 乗り物 | 時刻 |
| --- | --- | --- |
| 熊本駅 → 熊本駅前 | 徒歩 | 9:23 → 9:25 |
| 熊本駅前 → 藤崎宮前 | 熊本電鉄バス C9-5 | 9:25 → 9:46 |
| 藤崎宮前 → 藤崎宮前 | 徒歩（乗り換え） | 9:46 → 9:48 |
| 藤崎宮前 → 御代志 | 熊本電鉄 本線 | 9:55 → 10:21 |
| 御代志 → 御代志 | 徒歩 | 10:21 → 10:31 |

同じ問い合わせで、直通のバス（9:18 → 10:14）と、産交バスから電車に乗り継ぐ経路も返ります。
中継は、待ちを含めていちばん早く着く直通のバスを選びます。

収録の熊本のスポットどうし 100組（直線 1.5〜25km、平日の朝9時に出発）を聞いた結果です
（`node tools/otp_bench.mjs --pairs 100 --md`。4コアの機械、OTP は温まったあと）。

| 出発 → 到着 | 直線 | 距離の目安 | OTP（待ち込み） | 乗り物 |
| --- | ---: | ---: | ---: | --- |

  自分の機械なので、回数の制限もありません

## 距離からの目安との差し替え方針

旅程づくりは、いまも2段で時間を決めています（`packages/core/src/pipeline.js`）。

1. **目安で組む。** 距離からの目安（`feasibility.js` の `estimateMinutes`）で、行ける場所を選んで並べます
2. **実際の便で組み直す。** 並んだ順に、区間ごとに中継の `POST /transit` へ聞き、返った時刻で組み直します
   （入らなくなった場所は外し、理由を書きます）

決めたこと:

- **2段目は、OTP が入っていれば OTP から聞く。** この PR で、中継の自動の順の先頭に OTP を置きました。
  エンジンは何も変えずに、OTP の時刻で組み直されます。範囲の外は、今までどおりほかの API に回ります
- **1段目の目安は、まだ OTP に置き換えない。** 1段目は候補を絞るために何百組もの距離を比べるので、
  1回 0.15秒でも数十秒かかります。目安は「いつでも・すぐ・どこでも」出ることのほうが大事です
- **目安の速さは、別に直す。** 上の測定で、バスで動く区間の目安は実際の半分ほどでした。1段目で
  詰め込みすぎ、2段目で外す場所が多くなります。直すなら「公共交通で、地方の街」の目安を遅くする
  ことになりますが、旅程の成立率（`tools/plan_bench.mjs`）に効くので、JR を含む地域でも測ってから
  別の変更にします
- **JR は OTP の外。** JR の時刻表は公開されていないので、JR の区間は今までどおり駅すぱあと・
  Transit APIなどに任せます。OTP が強いのは、路線バス・私鉄・路面電車が主になる地方の街です
- **サイトとアプリには入れない。** OTP は自分で動かすサーバーです。ブラウザからは中継を通してだけ使います

## 地域を足すとき

`otp/regions/<地域>.json` を作ります（`kumamoto.json` と同じ形。`feeds` は
[GTFS データリポジトリ](https://gtfs-data.jp/) の事業者の ID と時刻表の ID）。

```sh
python3 tools/otp_fetch.py otp/regions/<地域>.json
OTP_REGION=<地域> docker compose --profile otp run --rm otp-build
OTP_REGION=<地域> docker compose --profile otp up -d otp
```

時刻表には期限があります（熊本電鉄電車は 2026-12-28 まで）。期限が近づいたら `otp_fetch.py` と
`otp-build` をやり直します。

GTFS-JP の古い版（第2版まで）の `translations.txt` は形が違い、OTP が組み立ての途中で止まります。
`otp_fetch.py` は、古い形のときだけこのファイルを外します（読み仮名と英語名だけで、経路には効きません）。

### なぜ熊本か

鉄道（熊本電鉄）・路面電車（熊本市電）・路線バス4社の時刻表が、どれも GTFS-JP で公開されていて、
「徒歩→バス→鉄道→徒歩」を1つの街で確かめられるからです。地図は九州の配布ファイル（350MB）を
熊本のまわりだけ切って 31MB にしています（`osmium`。無ければ切らずに使います）。

## ライセンス

データはリポジトリに入れていません（`data/otp/` は .gitignore 済み。`otp_fetch.py` で作り直せます）。
`data/otp/<地域>/SOURCES.md` に出典を書き出します。

| データ | ライセンス |
| --- | --- |
| 熊本電鉄電車 | CC0 1.0 |
| 熊本市電 | CC BY 2.1 JP |
| 熊本都市バス・熊本バス・熊本電鉄バス・産交バス | CC BY 4.0 |
| 道路・歩道 | © OpenStreetMap contributors（ODbL 1.0） |

経路の答えを画面に出すときは、答えた検索の名前（OpenTripPlanner）を出します。時刻表の
提供元の表示が要る使いかた（公開のサービスで出すなど）をするときは、各事業者の表示を足してください。
OTP 本体は LGPL-3.0 で、公式のイメージをそのまま使っています（改変していません）。
